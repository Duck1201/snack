# 09 — `@snack-ai/cli@1.0.0` installs the plugin at `0.1.2`, and tells anyone on `1.0.0` to downgrade

Status: `ready-for-agent`
Severity: **P1** — blocks release; ships as `1.0.1`
Owner: unassigned
Found in: Phase 1 end-to-end review, Wave 2, `@snack-ai/cli@1.0.0` from npm

## What happens

A clean OpenCode config, and the documented setup path from the stable release:

```bash
snack setup opencode --install-plugin --source oc --provider opencode --profile duck --plan pro
```

writes

```json
"plugin": [["@snack-ai/opencode@0.1.2", { … }]]
```

`opencode-config.js:17`:

```js
export const pluginPackageSpec = `${packageName}@0.1.2`;
```

The constant was never moved with the version. `@snack-ai/opencode@1.0.0` is published — `PLAN.md`
says the plugin "reached `1.0.0` alongside the CLI" — and the `1.0.0` CLI never installs it. Every
user who follows the documented setup gets `0.1.2`.

## The part that makes it P1

Pin the config at the newest published plugin by hand and ask `doctor`:

```
[warn] opencode_plugin: OpenCode live-capture plugin is registered at another version;
       re-run `snack setup opencode` to update it.
```

`doctor` calls `1.0.0` "another version" and sends the user to a command that would **downgrade**
them to `0.1.2`. The advice is not merely stale, it is backwards, and the hand-edit workaround is
undone by the next `setup` run while `doctor` keeps warning either way.

`inspectPluginRegistration` (`opencode-config.js:69`) is `plugin[0] === packageSpec ? "compatible" :
"outdated"` — a string comparison against the stale constant, so the newest artifact can only ever
be reported as outdated.

## What is not broken

Capture itself. The `0.1.2` plugin loads in OpenCode `1.18.10`, never throws into the host, and
writes a content-free spool — verified in Wave 2 and recorded in `spec.md`. The event contract is
`spool-event-v1` on both sides, which is why this is a wrong-version defect rather than a broken
one. The comment above the constant explains the design correctly:

> Compatibility is a property of the spool event contract, not of a version string: every
> `@snack-ai/opencode@0.1.x` emits `spool-event-v1`.

That reasoning is sound and is exactly why nobody noticed: the pairing works, so nothing failed.

## Suggested fix

`pluginPackageSpec` must be derived from the release rather than typed. The CLI already knows its
own version; the plugin's compatible range belongs in one place that the version bump cannot miss —
a field in the CLI's manifest, or the compatibility matrix read at build time. A hand-maintained
constant naming another package's version will go stale again at the next minor.

`release:check` should also assert that the spec the CLI would write matches a published version of
the plugin. This defect is exactly the shape `release:check` already learned to catch once, when it
was comparing a version string instead of content — see `.scratch/stable-release/spec.md`, "The
candidate tag earned its keep immediately".

## Test seam

`opencode-config.js` — assert `pluginPackageSpec` names the plugin version the workspace publishes,
read from `packages/opencode/package.json` rather than repeated as a literal. Red first: this fails
on `1.0.0` today.
