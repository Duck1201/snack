# Documentation lives in `docs/`, not in a GitHub Wiki

SNACK's documentation is a navigable set of pages under `docs/` in this repository, indexed from
`README.md`. There is no GitHub Wiki, and the `man snack` page is generated from the same source
rather than maintained separately.

The reason is delivery principle 11: a change to behavior, a flag, an output document, a supported
client, or an upgrade path is not finished until both the package `README.md` npm serves and the
repository documentation GitHub serves say so. That principle is only enforceable if documentation
travels in the same pull request as the code, under the same review and the same gate. A GitHub Wiki
is a separate git repository with its own history, editable through the web without a pull request;
no branch protection, no CI job, and no `release:check` can reach it. Choosing a wiki is choosing to
make the project's own documentation principle structurally unenforceable, which is a worse outcome
than the editing convenience it buys.

GitHub Pages over the same folder was the other option and remains available later: it is a
presentation layer over `docs/`, not a different home for it, so adopting it moves no content. It
was not taken now because it adds a generator, a build, and one more release artifact that has to
stay green, for a project whose documentation problem is structure rather than styling.

The `man` page is generated by a script from Commander's own command and flag definitions plus the
prose of the command-reference page, checked into the repository, and verified in `npm run check`. A
hand-written roff page rots on the first new flag, and this project has already written down that a
stale document is a defect against the release that left it stale. Generating it means a new flag
without documentation fails the gate instead of shipping a manual that lies.

Bilingual coverage follows what the reader is: the package READMEs, installation, command reference,
and troubleshooting exist in English and Portuguese, because those are what an installer reads.
Architecture, specification, ADRs, and the archived roadmap stay English-only — they are read by
people working on the code, and doubling them would mean four edits for every behavioral change,
which is the kind of cost that quietly stops being paid.
